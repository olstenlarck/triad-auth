# Monorepo

This is a Solidity/TypeScript/Rust monorepo for multiple projects and languages. It is managed by pnpm and Turborepo with the oxc toolchain through ultracite, Cargo for Rust, and Foundry Forge for Solidity.

- Always read and follow `~/skills/instructions.md` and its referenced files.
- Creating new solidity/foundry projects: copy `solidity/template/` as starting template, and edit the package.json fields, readme and etc.
- pnpm manages the workspace and Turborepo runs the tasks defined in `turbo.json`. `pnpm install` points `core.hooksPath` at `.githooks` through the `prepare` script, which installs the Git hooks; `prepare` skips that when `CI` is set to anything but empty, `0`, `false`, or `no`, and workflow commits pass `--no-verify`, so CI never runs the developer hooks. Both hooks run with `--affected`: pre-commit checks the packages with changes against HEAD, pre-push checks and tests what the push adds to master.
- use conventional commits
- Use turbo or pnpm filters to run commands inside a given project, package, or app.
- Solidity dependencies are managed by Pnpm through Nodejs/node_modules.
- Solidity projects are in `solidity/*`.
- TypeScript packages and projects are at `packages/*`.
- Package PRs include a Changeset. Publishing goes through the committed scope mapping to `npm.wgw.lol`: locally with the GitHub CLI token, in CI with Depot CI OIDC that pnpm exchanges at the registry worker. The worker trusts only tokens for this repository on `master` from Depot organization `pcnr2v598s`, and reads the `workflow_ref` claim: `publish-nightly.yml` may write `nightly` and `publish-prod.yml` may write `latest`. The publishing workflows need no registry secrets.
- Unscoped packages, such as `zagora`, publish to npmjs.com from GitHub Actions, because npm trusted publishing accepts OIDC tokens only from GitHub-hosted runners. `.github/workflows/npm-publish-nightly.yml` and `.github/workflows/npm-publish-prod.yml` mirror the Depot publishing workflows for those packages. Each one first calls `.github/workflows/wait-for-ci.yml`, which polls the Depot `ci / check`, `ci / test`, and `ci / build` check runs of the pushed commit, because `workflow_run` cannot follow a Depot workflow. npm trusts `npm-publish-nightly.yml` in the `nightly` environment and `npm-publish-prod.yml` in the `latest` environment, and both environments allow only `master`. The Depot workflows skip the unscoped packages, and the GitHub workflows skip `@tunnckocore`. `pnpm run packages:publish <vlt|npm>` filters the Changesets publish plan to one share, packs it, and publishes it. Both use the one release PR from `prepare-publish`. An unscoped package needs a `repository` field that names `tunnckoCoreHQ/monarch`, because npm checks it against the provenance.
- CI runs on Depot CI from `.depot/workflows/`. Every job checks out, then runs the composite action `.depot/actions/setup`, which installs Socket, pnpm, Node, the workspace, and Foundry when `solidity: true`. Every push to `master` runs `ci`: `check`, then `test`. When `ci` succeeds, `publish-nightly`, `prepare-publish`, and `publish-prod` start through `workflow_run`. Every publishing workflow first runs `turbo run build` for only the packages it publishes, which runs their `build` scripts and those of their dependencies in dependency order with caching, then publishes in dependency order: the nightly workflows filter to the packages they publish, and `packages:publish` filters to its share, so the GitHub workflows never build `@tunnckocore` and the Depot workflows never build the unscoped packages. A package that emits or bundles declares a `build` script; tests always import source. `publish-nightly` snapshot-versions pending Changesets and publishes only the packages that push changed, with the `nightly` dist-tag. `prepare-publish` opens or updates the release PR from pending Changesets on every push and has no OIDC token. `publish-prod` runs only for the merged release PR commit and publishes stable versions with `latest`, package tags, and GitHub Releases; if that publish fails, dispatch `publish-prod` on `master` (`depot ci dispatch` or the Depot dashboard) and it publishes whatever is still missing. The owner reviews and merges release PRs by hand; never enable auto-merge on them.
- Open pull requests with `gh pr create`, then enable auto-merge at once with `gh pr merge --auto --squash`. Never merge by hand. GitHub merges when the master ruleset is satisfied, and that merge triggers the master workflows. Release PRs are the exception above: the owner merges them by hand and nobody enables auto-merge on them.
- The master ruleset requires the Depot CI `ci / check`, `ci / test`, and `ci / build` checks, the `do-not-merge` check, the `review` status, one approval of the latest push, and resolved review threads. New commits dismiss earlier approvals.
- Greptile reviews every pull request except Dependabot and release PRs when it opens, and approves clean ones. It does not re-review on push: after fixing its findings, reply, resolve the threads, and comment `@greptileai review` to request a re-review.
- The Flue review agent in `packages/review-agent` reviews every same-repository pull request except Dependabot PRs and the release PR (olstenlarck's `changeset-release/master`) through `.github/workflows/review.yml`: when it opens, then on every push the commits after the last one it reviewed. It runs with `flue run` on OpenCode Zen, by default the free `muse-spark-1.3-contributor-free`, with the `OPENCODE_API_KEY` of the `review-agent` GitHub environment, and posts as `olstenlarck` with `OLSTENLARCK_HQ_PAT`. A `/review` comment from tunnckoCore runs a full review again, and `/review <model>` switches the Zen model for that pull request. Reply in one of its threads to answer a finding (only the owner, members, and collaborators start it): it replies, and it resolves the thread when it agrees. When it agrees that a finding does not apply, it records the decision in the `REVIEW.md` of that project (or the root one), and the workflow commits it to the pull request with the job token, so `olstenlarck` is never the last pusher and the commit starts no workflow runs; later reviews read these files, so keep them. Its `review` commit status is pending until it has reviewed the head commit and while one of its threads is unresolved; then it turns green and `olstenlarck` approves the head commit, except on pull requests that `olstenlarck` opened. Dependabot and release PRs get success without a review or approval. `/approve` from tunnckoCore stays as a manual fallback. A thread resolved by hand updates the status only at the next push or review comment. To retry a failed review, re-run the workflow or comment `/review`.
- Do not approve a pull request unless the user says so, and then only with every thread resolved, a Greptile score of 5/5, and green checks.
- A `do-not-merge` label holds the pull request: the `do-not-merge` check fails while it is present and auto-merge waits. Do not remove the label. Keep babysitting the pull request meanwhile.
- Push to `master` directly only when the user asks; the pre-push hook runs the checks. Everything else goes through a pull request.
- Dependabot PRs are approved and auto-merged by `auto-merge-deps` with the `OLSTENLARCK_HQ_PAT` secret. Socket Optimize runs on Depot CI and pushes verified overrides straight to master with the same PAT, opens a `socket optimize: needs attention` PR when verification fails, and an issue when it fails before producing changes.
- Apps and docs sites are at `apps/*`.
- Chrome extensions are at `chrome-extensions/*`, one directory per extension, loaded unpacked in the browser. They have no build step and no tests, only a `check` script.
- Solidity projects' docs should be on their own `solidity/*/docs` folder.
- The TypeScript toolchain is oxlint and oxfmt with the ultracite presets, type-aware linting and type checking through tsgolint, and Vitest. Every app and package has `check` (`ultracite fix`, which formats, lints, and type-checks) and `test` (Vitest) scripts that run from its own directory with the root configs, so turbo caches each package on its own. The root package has `check` for the root files only.
- Solidity projects are formatted, linted, and built with Foundry, not pnpm or oxc.
- Every `check`, `test`, `fmt`, `lint`, `build`, `deploy:nightly`, and `deploy:prod` script is a turbo task: run them with `turbo run <task> --filter=<package>` across packages, never with pnpm filters. The deploy tasks never cache. Every other script runs with `pnpm run <script>` inside its package or `pnpm --filter <package> run <script>` from the root. Binaries run with `pnpm exec`.
- Solidity formatting, linting, tests, and builds run through the root scripts, each a filtered turbo run. `pnpm run solidity:check` runs fmt and lint for every Solidity project with caching, `pnpm run solidity:test` runs only the tests with caching, and `pnpm run solidity:test:fresh` runs all project test scripts in parallel without cache for a fresh fuzz. `pnpm run solidity:fmt`, `solidity:lint`, and `solidity:build` run that one script in every project. Prefer the per-project filter for day-to-day work.
- For changes within one Solidity project, run `turbo run check --filter=<project>`; use the root `pnpm run solidity:check` when changes span Solidity projects, without repeating the filtered check.
- `turbo run check test` runs everything, TypeScript and Solidity, and is what the pre-push hook runs; pre-commit runs `turbo run check`. `turbo run check --filter=<package>` does one package and `turbo run check --affected` does what the branch changed.
- Call `turbo run test --filter=glyph-protocol` to run Solidity tests only for that project. Other project scripts run with `pnpm --filter glyph-protocol <script>`.
- Every Solidity/Foundry project has `fmt`, `test`, `lint` and `build` scripts.

Turbo filter patterns:

```
Filter Patterns:
  --filter //               Select the repository root only
  --filter <pattern>        Select by package name (e.g. foo, @scope/*)
  --filter ./<dir>          Select packages under a directory
  --filter {<dir>}          Same as ./<dir>, but allows traversal suffixes
  --filter <pattern>...     Select package and its dependencies
  --filter ...<pattern>     Select package and its dependents
  --filter <pattern>^...    Select only the dependencies (exclude the package itself)
  --filter !<pattern>       Exclude packages matching the pattern
```

## Apps and deployments

- Every app lives in `apps/<name>` with its own `package.json`, `alchemy.run.ts`, and a `tsconfig.json` that extends the root one. Depot CI deploys apps through Alchemy; GitHub Actions only checks them. No app uses Cloudflare Workers Builds or the `cf` CLI any more.
- `master` is nightly for every app: `deploy-nightly` deploys what a `master` push changed. Production is a `deploy-prod` run started by hand.
- One Depot CI pull request workflow in `.depot/workflows/` covers the whole workspace. `ci` runs `turbo run check` and `turbo run test` for every package on every pull request and on pushes to `master`, with `--affected` on pull requests; `publish-nightly`, `prepare-publish`, and `publish-prod` follow it on `master`. `build` builds the npm packages and the Solidity projects in the same workflow. Turbo's remote cache on Depot CI is Depot Cache, so unchanged tasks replay across runs. A new app or package needs no workflow of its own. The master ruleset requires the Depot checks `ci / check`, `ci / test`, and `ci / build`. `auto-merge-deps`, `do-not-merge`, `review`, and the npm publishing workflows stay on GitHub Actions; `socket-optimize` runs on Depot CI on a schedule.
- Never run an app's `deploy` script locally unless the user explicitly asks. CI flows runs what's needed when needed.

## Alchemy apps

- Alchemy apps deploy with the Alchemy CLI, not `cf` or Workers Builds. The stack is `alchemy.run.ts` in the app folder and replaces `cloudflare.config.ts`. Astro apps use `Cloudflare.Website.Astro`, which injects the adapter, so `astro.config.*` declares none.
- State lives in the remote Cloudflare state store, `Cloudflare.state()`. Local deploys use the `cf-equator` Alchemy profile.
- Alchemy apps deploy through `deploy:nightly` and `deploy:prod` scripts. Solidity projects keep `deploy`, and CI never runs it.
- A prod-only app has only `deploy:nightly`, and it deploys the `prod` stage. `apps/x402-router.wgw.lol`, `apps/npm.wgw.lol`, and `apps/badges.wgw.lol` are that shape.
- The registry worker at `apps/npm.wgw.lol`, `vlt-npm-wgw-lol`, gets its VLT service tokens and upstream registry URL at deploy time from the `VLT_READ_TOKEN`, `VLT_WRITE_TOKEN`, and `VLT_UPSTREAM_URL` Depot secrets, which only `deploy-nightly` passes. Change a value with `depot ci secrets set`, then redeploy: the next deploy overwrites a secret set on the Worker directly.
- The badges worker at `apps/badges.wgw.lol`, `badges-wgw-lol`, serves the README badges for Depot CI workflows and jobs. It reads a Depot organization token from the `BADGES_DEPOT_TOKEN` Depot secret, bound under the same name, which only `deploy-nightly` passes. `/<owner>/<repo>/<workflow>/<job>.svg` renders the job status of the newest finished `push` run with the `badgen` library, `.json` returns the same `{ subject, status, color }`, and the path without an extension redirects to that job in the Depot dashboard. The workflow-level `.svg` and `.json` show the workflow status, and the workflow path without an extension redirects to `https://depot.dev/products/ci`. `/<owner>/<repo>/socket` returns the badgen.net GitHub checks badge of the `Socket Security: Project Report` check on `master`, with `passing` and `failing` in place of `success` and `failure`. The Worker's own badges have the badgen `black` label color. `/health` returns the deployed commit.
- An app with both environments has both scripts and two Workers. `apps/triad-auth` is that shape: `deploy:nightly` deploys the `nightly` stage to `triad-auth-nightly` and `deploy:prod` deploys the `prod` stage to `triad-auth`, each with its own D1 database that Alchemy migrates on deploy. Its ten secrets are Depot secrets under the same names the stack reads. `BETTER_AUTH_SECRET`, `IDENTIFIER_SECRET`, `RATE_LIMIT_SECRET`, and `ENCRYPTION_SECRETS` differ per Worker through Depot variants: `nightly` is scoped to `deploy-nightly.yml` and `prod` to `deploy-prod.yml`. The six OAuth provider values are one default variant shared by both. The app's `promote` script dispatches `deploy-prod` for the app alone; run it only when the user asks.
- `deploy-nightly` runs after `ci` succeeds on a `master` push. It runs `turbo run deploy:nightly --affected` for what that push changed.
- `deploy-prod` runs only by hand: `pnpm run apps:deploy:prod` from the root. It runs `deploy:prod` for every app that has it, or for one app with the `app` input.
- Both workflows read the `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` Depot secrets and pass the deployed commit as `COMMIT_SHA`. The token is an account-owned Cloudflare API token, created in the dashboard, because Alchemy OAuth logins cannot mint tokens.
- Never run a `deploy:nightly` or `deploy:prod` script locally unless the user explicitly asks.
